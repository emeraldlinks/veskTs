# LSP Volar Migration — Ripple Study & Vesk Plan

> Finding report: how Ripple (github.com/Ripple-TS/ripple) implements its LSP on the
> Volar framework, and how vesk replaces every ripple/tsrx piece with its own.
> Source studied: `Ripple-TS/ripple@main` (cloned to `/tmp/opencode/ripple`).

## 1. Why this replaces everything we built

Our current LSP (`packages/lsp`, 15 heuristic modules, ~5,200 lines) works by string scanning:
regex import parsing, `lines[i].includes(...)` navigation, static knowledge lists, a hand-written
"component prop type extractor". It is not TypeScript-aware. Ripple's LSP is the opposite: a
**Volar language server** where every language feature runs against a *virtual TypeScript file*
generated by the compiler with **offset mappings**. TS does hover/completions/diagnostics/
navigation/rename/references — Volar maps results back to `.vsk` positions.

Vesk's compiler already ships `vskToTsx` (the virtual-file generator) and `typecheckProject`
(the ambient-declared TS program). What's missing is (a) a mapping-aware codegen and
(b) the Volar wiring. Ripple proves the architecture; vesk supplies the compiler.

### 2.1 The Volar language plugin (heart of the system)

`getRippleLanguagePlugin()` returns a `LanguagePlugin<URI, VirtualCode>`:

- `getLanguageId(f)` → `'ripple'` for `.tsrx`.
- `createVirtualCode(fileName, languageId, snapshot)` → `TSRXVirtualCode` (id `'root'`,
  languageId `'ripple'`).
- `updateVirtualCode()` → recompiles from the new snapshot.
- `typescript.extraFileExtensions` → `[{ extension: 'tsrx', isMixedContent: false, scriptKind: TSX }]`.
- `typescript.getServiceScript(code)` → the virtual code *is* the TSX service script
  (`extension: '.tsx'`, `scriptKind: TSX`), so `volar-service-typescript` runs against it.

`TSRXVirtualCode` implements `VirtualCode`:

- `generatedCode` — the TSX produced by `compile_to_volar_mappings(source, filename, { loose: true })`.
- `mappings` — `CodeMapping[]` (Volar `@volar/language-core` shape, below).
- `embeddedCodes` — CSS blocks (`languageId: 'css'`) and `<script>` bodies
  (`languageId: 'typescript'`), each with a single region mapping.
- `snapshot` — `getText/getLength/getChangeRange` over the generated code.
- `fatalErrors` / `usageErrors` — compiler diagnostics surfaced by a plugin.
- On compile failure: feeds the RAW source back as generated code with a 1:1 completion-enabled
  mapping so TS can point at the broken construct and completions keep working.

`CodeMapping` shape (Volar 2.x):

```ts
interface CodeMapping {
  sourceOffsets: number[];
  generatedOffsets: number[];
  lengths: number[];
  generatedLengths?: number[];
  data: CodeInformation; // flags: verification, completion, semantic, navigation,
                         // structure, format (+ customData: Record<string, unknown>)
}
```

`mapping_data` presets in `source-map-utils.js`:

- `mapping_data` = `{ verification, completion, semantic, navigation, structure: true, format: false }`
- `mapping_data_verify_only` = `{ verification: true }`
- `mapping_data_verify_complete` = `{ verification, completion }`
- `mapping_data_completion_only` = `{ completion }`
- `mapping_data_string_span` — semantic with `shouldHighlight: () => false` (identifier inside a string)

### 2.2 Compiler-side codegen (how mappings are produced)

`tsrx` compiles `.tsrx` → TSX by AST transform + **esrap reprint** (a real source map), then
`convert_source_map_to_mappings` walks the *source* AST and emits one `CodeMapping` per token:

- `visit_source_ast` collects CSS/style and script regions from the source AST.
- For each node with a location, `generated_offset_for_text` finds the generated position of
  the node's opening text via the source map, then records a mapping.
- `add_export_mapping` gives full declaration spans (multi-point mappings with `lengths: [0, 0]`).
- `add_diagnostic_mappings` adds narrow 1:1 mappings for parser-error positions so the
  diagnostic plugin can translate them.
- `create_volar_mappings_result({ ast, ast_from_source, source, generated_code, source_map,
  post_processing_changes, line_offsets, errors })` ties it together.
- Post-processing insertions are recorded as `post_processing_changes` (offset deltas) and
  folded into the src→gen map.

Key insight for vesk: **esrap is only needed because tsrx reprints ASTs**. Vesk's `vskToTsx`
emits verbatim `source.slice(start, end)` text — every emitted chunk already knows its source
range. We can produce `CodeMapping`s directly while emitting (no source map, no decode).

### 2.3 LSP server (`language-server/src/server.js`)

`createTypeScriptProject(ts, undefined, ({ configFileName, projectHost, sys }) => ...)`:

- `wrapCompilerOptionsProvider` monkey-patches `getCompilationSettings` to inject Ripple
  defaults (`resolveConfig`: ESNext target, lib es2022+dom+dom.iterable, typeRoots discovery).
- `languagePlugins: [getRippleLanguagePlugin(...)]`, with a `setup({ project })` hook that
  also wraps the project's own host + tracks tsconfig dependency files.
- Plugins list (order matters):
  1. `createAutoInsertPlugin` — `>` auto-close (void elements), on-type formatting.
  2. `createCompletionPlugin` — ripple syntax completions (tracked collections with
     auto-imports, directives, etc.) merged on top of TS completions.
  3. `createCompileErrorDiagnosticPlugin` — compiler `fatalErrors`/`usageErrors` →
     LSP diagnostics, mapped through the source map; suppresses TS diagnostics while a
     fatal compile error exists.
  4. `createDefinitionPlugin` — special-case definitions (package entry files, type-def file
     matching), falling back to `typescript-semantic` results.
  5. `createDocumentSymbolPlugin` — ripple-aware outline.
  6. `stripDocumentFormatting(createCssService())` — CSS service, formatting stripped.
  7. `...createTypeScriptServices(ts).map(stripDocumentFormatting)` — the TS engine.
  8. `createTypeScriptDiagnosticFilterPlugin` — wraps `typescript-semantic.provideDiagnostics`:
     drop TS diagnostics while fatal compile errors exist; honor per-mapping
     `customData.suppressedDiagnostics` codes.
  9. `createHoverPlugin` — wraps `typescript-semantic.provideHover`: rewrites hover contents
     via `customData.hover` (string | function | false) found on the mapping under the cursor.
  10. `createDocumentHighlightPlugin` — ripple-aware highlight.
- `workspaceState.js`: watches `**/*.tsrx`, ts/tsx/js/json, lockfiles, package.json;
  `isPackageStateFile`/`isTypeScriptConfigFile` classify changes → restart process or reload.
- `handleWorkspaceChanges` + `server.fileWatcher.watchFiles` on initialized.

### 2.4 VSCode extension (`vscode-plugin/src/extension.js`)

- Activates on `**/*.tsrx`; `documentSelector: [{ language: 'ripple' }]`.
- `server.js` = `createRippleLanguageServer()` import of the language-server package.
- `@volar/vscode`: `activateAutoInsertion([{ language: 'ripple' }], client)`,
  `createLabsInfo(protocol)` for Volar Labs.
- **Runtime patch of the built-in TS extension** (`patchTypeScriptExtension`): intercepts
  `fs.readFileSync` of `vscode.typescript-language-features/dist/extension.js` before its
  activation and string-replaces the language-mode lists:
  `t.jsTsLanguageModes=[...]` → `.concat("ripple")` and
  `.languages.match([...]` → `.concat("ripple")`. This makes the TS extension treat `.tsrx`
  as TypeScript-like so its commands/UI work — *without* double-loading a TS plugin.
- `setupDynamicContexts`: `editorLangId` / `resourceLangId` / `typescript.isManagedFile` /
  `supportedCodeAction` contexts gating TS menu contributions (`menus` in package.json).
- `configurePrettier`: sets `prettier.documentSelectors` + `[ripple]` default formatter to
  the Prettier extension (they do NOT register their own formatter).
- TS Go (native preview) is detected and warned against.
- `addCustomCommands`: `ripple.goToSourceDefinition` (executes definition provider, prefers
  `.tsrx` targets over `.d.ts`).

| `createCompletionPlugin` | vesk completion plugin: `&[...]` track decls, event handlers, Tailwind classes, vesk intrinsics (`effect`/`derived`/...), HTML docs — merged over TS completions |
| `createAutoInsertPlugin` | `>` auto-close port |
| `createDocumentSymbolPlugin` | port (or TS symbols) |
| `createDefinitionPlugin` | `.vsk` import specifier → file resolution (TS handles the rest via `.vsk.d.ts`) |
| `resolveConfig` (target/libs/typeRoots defaults) | vesk defaults: `jsx: preserve`, ES2022, lib es2022+dom+dom.iterable; `types: []` |

| `vscode-plugin/src/extension.js` | rewrite `extension/vsk-vscode/src/extension.ts` (patch TS extension for `vsk`, contexts, Prettier, auto-insert, `vesk.restartLsp` kept) |
| `@tsrx/prettier-plugin` as default formatter | `@vesk/prettier-plugin` |

### 3.1 Vesk-specific codegen differences (vs tsrx)

- **No reprint needed.** `vskToTsx`'s emission is `source.slice(a, b)` per statement — convert
  the `tsxEmit*` walk to emit segments `{ text, srcStart, srcEnd, data }` and record
  `CodeMapping`s inline. Output must stay byte-identical to today's `vskToTsx` (keeps
  `vsk-tsx.test.ts` / `ts-support.test.ts` / `typecheck.test.ts` green).
- **Track-decl typing.** Today: `const &[count] = track(0)` → `let count: any = track(0);`.
  For the LSP we can emit typed cells:
  `const __cell = track(0); let count = __cell.get(); let rawCell = __cell;` so hover shows
  `number`, not `any` (Cell<T> declares `get(): T`). Keep `vskToTsx` (tsc-in-.vsk) untouched;
  this is a codegen option (`typedCells: true`) used by the LSP only. Test both modes.
- **Component headers.** `component X(props)` → `function X(props)` — same-length prefix trick
  isn't needed: the header is one segment with a source range; the `component`→`function`
  keyword replacement maps to the same source span (keyword-level mapping, like tsrx's
  `add_export_mapping`).
- **Statement-mode bodies.** Re-emitted line-by-line with re-indentation — every statement is
  still a verbatim slice, so per-statement mappings are exact. Unmapped (synthetic)
  whitespace/indent gets no mapping.
- **`blankForClauses`** blanks `for (...)` JSX-text clauses to spaces — the blanked text is
  same-length, so slice offsets are unchanged; emitted blanks get no mapping (or
  `completion_only` for mid-typing directives).
- **`declare const Head` prepend** becomes an unmapped raw prefix segment.
- **CSS `style` blocks**: keep out of the TSX (as today) but emit embedded `css` virtual
  codes with region mappings (volar-service-css gives CSS intellisense).

### 3.2 Ambient declarations for the LSP

`typecheck.ts` holds `AMBIENT` (JSX.IntrinsicElements index signature, `Cell<T>`, `track`,
`derived`, `effect`, `untrack`, `peek`, `tick`, `flushSync`, `on_destroy`, `createContext`,
`useFetch`, router/params helpers, action/form/validators, Link/NavLink/Outlet/Image/Portal/
schema components, `redirect`, `notFound`, `createResource`, `getAction`, ...) and
`RUNTIME_OVERRIDE` (`import '@vesk/runtime'; declare module '@vesk/runtime' { track; derived }`).

Volar's `createTypeScriptProject` builds its program from the user's tsconfig — the ambient
must be injected. Plan: in `setup({ project })` (same hook Ripple uses for compiler options),
patch the project's language-service host:

- `getScriptFileNames` → append `<appDir>/__vesk_ambient.d.ts` and
  `<appDir>/__vesk_runtime_override.d.ts` (appDir = `app` or `src/app`),
- `readFile` / `getScriptSnapshot` / `fileExists` → serve AMBIENT / RUNTIME_OVERRIDE,
- `resolveModuleNameLiterals` → `.vsk` and `.css` imports resolve to `*.vsk.d.ts` /
  `*.css.d.ts` (exactly like `createTypecheckHost`),
- `getCompilationSettings` → vesk defaults (jsx preserve, libs, types: []).

`__vesk_ambient.d.ts` is already in `typecheck.ts`'s `SKIP_FILES`, so if the CLI ever writes it
to disk nothing double-loads.

### 3.3 The smoke-test contract (must keep passing)

`packages/lsp/tests/lsp-smoke.mjs` (36 assertions today) maps onto the new stack:

- diagnostics: `undefinedVar` (TS TS2304 ✓), Card not "unknown component" (TS resolves local
  function ✓), `track` not unused (TS ✓) — drop our regex checks entirely.
- attr completion on `<Card `: includes `props`, excludes used `title`/`body`, includes
  `onClick` → TS gives `props` (Card's param) and used-attr filtering; `onClick` is NOT a TS
  prop → **our completion plugin adds event handlers** (ported from `knowledge.js`).
- expression completion inside `{count}`: `count`/`track` (TS scope ✓), `props`/`console`
  (TS gives console; `props` only when in scope — **completion plugin adds vesk intrinsics +
  props overlay** to keep the contract).
- hover onClick `clicked` docs → `customData.hover` on event-handler attribute mappings
  (hover plugin).
- hover Card `title`/`body` → `customData.hover` on component tag mappings (or TS quick info
  on the function) + props table.
- hover `<h1>` HTML docs → customData hover on JSX element mappings.
- hover `count` reactive binding (number OR reactive) → customData.hover on the track-decl
  mapping (typedCells makes TS type `number` too).
- hover typed prop `value` → TS quick info on the JSX attribute (`value: number`) ✓.
- hover `IFoo` interface → TS ✓ (virtual file keeps interfaces verbatim).
- hover `posts` → `Post[]` + `useFetch` source → TS ✓ (ambient `useFetch<T>(...): T`).
- signature help `track(` → TS ✓ (ambient).
- document symbols `Card`/`Home` → volar-service-typescript symbols over mapped code ✓.
- formatting (messy doc → prettier output) → keep a server-side formatting plugin running
  `prettier` + `@vesk/prettier-plugin` on `.vsk` docs (Ripple instead delegates to the
  Prettier extension; our smoke test exercises the server, so the plugin is required).
- definitions: `Card`, imported `helper`, `track` → runtime, reactive `count` → TS mapping ✓.
- rename `count` → ≥3 edits through the mapping ✓.

## 4. Implementation plan

### Phase 1 — compiler: mapping-aware codegen
1. Refactor `packages/compiler/src/vsk-tsx.ts` emission into a segment-based writer
   (`VskCodegen`: `add(text, srcStart?, srcEnd?, data?)` + `CodeMapping[]`), keeping
   `vskToTsx` byte-identical; add `typedCells` option for track decls; export
   `compileVskCodegen(source, opts) → { code, mappings, errors, styleRegions }`.
2. Tests: extend `vsk-tsx.test.ts`-adjacent suites (`vsk-codegen.test.ts`): mapping invariants
   (every mapping inside bounds, sorted, correct lengths; statement+expression modes),
   typedCells typing, style-region extraction, byte-identity of `vskToTsx`.
3. Run: `npx tsx packages/compiler/src/vsk-tsx.test.ts`, `ts-support.test.ts`,
   `typecheck.test.ts`, `track-codegen.test.ts`; then `build-packages.ts`.

### Phase 2 — LSP package rewrite (Volar)
4. `packages/lsp/package.json`: deps `@volar/language-server ~2.4.28`, `@volar/language-core
   ~2.4.28`, `@volar/source-map ~2.4.28`, `volar-service-css 0.0.70`, `volar-service-typescript
   0.0.70`, keep `@vesk/compiler`, `prettier`, `@vesk/prettier-plugin`.
5. Delete old modules (`analysis.ts`, `components.ts`, `completions.ts`, `context.ts`,
   `css.ts`, `diagnostics.ts`, `features.ts`, `formatting.ts`, `hover.ts`, `knowledge.ts`,
   `navigation.ts`, `project.ts`, `symbols.ts`, `text-utils.ts`, `type-utils.ts`, `types.ts`).
6. New `src/`:
   - `language-plugin.ts` — `getVeskLanguagePlugin()` + `VeskVirtualCode`
   - `server.ts` — `createConnection` + `createServer` + `createTypeScriptProject` + host
     patches (ambient injection, `.vsk` module resolution, compiler defaults) + plugin list
   - `plugins/compile-errors.ts`, `plugins/ts-filter.ts`, `plugins/hover.ts`,
     `plugins/completions.ts`, `plugins/auto-insert.ts`, `plugins/format.ts`,
     `plugins/definition.ts`, `plugins/symbols.ts`
   - `knowledge.ts` — ported HTML/event/attr docs + vesk intrinsics (survives from today)
7. Typecheck `packages/lsp` (`tsc --noEmit`).

### Phase 3 — bundle & extension
8. `scripts/build-lsp.js`: bundle new `server.ts` → `extension/vsk-vscode/lsp-server/index.mjs`
   (+ copy to `extension/vsk-neovim/lsp-server/index.mjs`).
9. `extension/vsk-vscode`: rewrite `src/extension.ts` (Ripple-style: activate on
   `**/*.vsk`, `@volar/vscode` auto-insert + labs, TS-extension patch for `vsk`,
   dynamic contexts, Prettier default, `vesk.restartLsp` + `vesk.goToSourceDefinition`);
   add `src/server.js` entry; update `package.json` (deps `@volar/vscode`,
   `vscode-languageclient`; menus with `resourceLangId == vsk`); keep grammar +
   language-configuration.

### Phase 4 — tests & docs
10. Port `lsp-smoke.mjs` (same 36 assertions, plus new: typed track hover via typedCells,
    `.vsk` import resolution, TS error suppression while compile-error present).
11. New unit tests: codegen mappings (compiler), language-plugin virtual code (LSP).
12. Full: `npm run test:unit` + LSP smoke + `node hydration-test.mjs`; update `AGENTS.md`
    LSP section, `packages/lsp/README.md`, extension docs, `llms.txt`, `TODO.md`.

## 5. Risks / notes

- Volar 2.4.28 + volar-service-typescript 0.0.70/0.0.71: volar-service-typescript 0.0.71 may
  pull newer `@volar/*` — pin service 0.0.70 to match Ripple's known-good combo, or test 0.0.71.
- Bundling: `@volar/*` + `volar-service-*` are ESM; rollup with `external: []` bundles them
  (like `typescript` today). Bundle size will jump (~3–5 MB) — acceptable for a server.
- The `setup` hook monkey-patches mirror Ripple's own `wrapCompilerOptionsProvider` —
  this is the established pattern, not a hack we're inventing.
- Keep `vskToTsx` byte-identical: the segment refactor is the riskiest step; the compiler
  test suites are the safety net.
- Grammar (TextMate) stays; semantic tokens come from Volar's TS service — the old
  `semanticTokensProvider` hand-rolled legend is deleted.
